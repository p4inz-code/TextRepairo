## 3. Work packages (build order)

Order matters: the test set and security come first, features after. Each package lists what changes and how we know it is done.

### WP1 — Test and eval foundation (first)
- Grow `eval/cases.jsonl` from 60 to about 150: slang/chat shorthand, Hinglish and romanized Hindi/Marathi input, all-caps, emoji, mixed scripts, lists/markdown, already-correct text (must come back unchanged), long jumbled input, **30 more injection cases**, and a Style × Formality sample (not the full cross product).

- Done when: new cases exist, the runner reports the AI-tell score, current v0.1 prompts have a recorded baseline.

### WP2 — Real progress bar (end to end)
How it stays honest:
- Work is split into the existing chunks. Each chunk's weight = its share of the total characters. Known up front, exact.
- **Reading phase:** real % from llama-server's `prompt_progress` (processed / total tokens).
- **Writing phase:** tokens generated ÷ expected tokens (expected = the chunk's real token count from the engine's `/tokenize`, since a repair is about as long as its input). This part is an estimate, so it is capped at 99% of the chunk until the chunk is actually finished. The bar never goes backwards and only reaches 100% when the result is done.
- **Model loading** cannot be measured, so it is shown as an honest "Loading model… 6s" with a real timer, not a fake percentage.
- **Time left** is computed from measured speed, shown only after enough data (about 3 s and 5%), and labeled "about".
- Engine emits `{"event":"progress", chunk, chunks, phase, pct, tokens_per_s, eta_s}` over the existing SSE stream; `server.py` passes it through; `app.js` renders it.
- UI: bar in the result pane and a slim copy in the action bar; text like "Part 3 of 7 · 42%"; `role="progressbar"` with `aria-valuenow`; respects reduced motion; Stop still works.
- Same real counter in the CLI (stderr, one updating line when on a terminal) and in the Doctor model-hash check.
- Files: `engine.py`, `server.py`, `web/app.js`, `web/style.css`, `cli.py`, new `progress.py` (pure math, unit-tested).
- Done when: unit tests prove monotonic, ≤100, and weights sum correctly; a real 8k-character run on your Standard model shows a steadily moving bar that hits 100% only at completion; I record how close the time-left estimate was.

### WP3 — Text limit
- Hard cap **10,000 characters** (your number). One constant in `config.py`. I will not add a setting to change it unless you ask.
- Live counter "8,430 / 10,000", turns amber at 90%. Over the cap: Repair is disabled with a plain message. Text is never silently cut. Server enforces the same cap (clear error), CLI has `--max-chars`.
- Done when: client and server tests pass for exactly-at-cap, one over, and Unicode (counts characters, not bytes).

### WP4 — History (default on, local)
- Storage: SQLite file `history.db` in the data folder (Python standard library, no new dependency). Fields: time, style, formality, input, output, model, seconds, warning count.
- **Cap: newest 100 kept; entry 101 permanently deletes the oldest.** `PRAGMA secure_delete=ON` plus periodic `VACUUM` so deleted text is really gone from the file.
- UI: History panel (custom, in the app): list with time and snippet, click to restore input and result, delete one, **Clear all** (custom confirm). Count shown "37 of 100".
- Settings → Privacy: History on/off, **Private mode** (nothing saved while on, small "Private" tag always visible), "Forget on exit", Open data folder.
- CLI: `textrepairo history list|show|clear`, `--private` flag.
- No telemetry, no uploads, never logs your text. `PRIVACY.md` states exactly what is stored.
- Files: new `history.py`, `server.py` endpoints, `web/*`, `cli.py`, `PRIVACY.md`.
- Done when: tests prove the 101st insert removes the oldest, private mode writes nothing, clear really empties the file.

### WP5 — Human-sounding output by default
- `prompts.py` `CORE_RULES` gains a "write like a person" block, **written in our own words** from the humanizer skill's principles: no inflated or promotional wording, no stock openers/closers, no padding with threes or "not only… but also", no chatty framing, plain verbs, natural contractions when the register allows, varied sentence length, no added emoji/bold/headings, never add claims or facts. I will read the skill at build time and check its licence before reusing any wording.
- Few-shot examples rewritten to match. `PROMPT_VERSION` → "4".
- **Deterministic safety net** (`humanize.py`): a small pass that removes known AI stock phrases and em-dash overuse **only if the phrase was not in your original text**, so it never changes words you wrote.
- AI-tell score from WP1 is the measurement. Target: lower than v0.1 on every style, with no drop in the meaning-preservation checks.
- Claim discipline: we say "natural-sounding", never "undetectable by AI detectors".
- Done when: eval shows the score fell and the 20 cases that passed before still pass.

### WP9 — Security hardening
1. **Session cookie instead of URL token.** The launch link `?t=` is exchanged once for an HttpOnly, SameSite=Strict cookie and redirected, so the token never sits in history or JS. Origin check on every write request.
2. **CSP and headers:** `default-src 'self'`, no inline script, `frame-ancestors 'none'`, `nosniff`, `no-referrer`, `Cache-Control: no-store` on `/api`. (I will remove any inline styles/scripts that conflict.)
3. **Limits:** one repair at a time (queue), request-size caps, SSE timeouts.
4. **Hash pinning for the llama.cpp runtime download**, same as the models (I will verify what `runtime.py` does today and close the gap).
5. **Logs:** never include user text; redact home paths in reports.
6. **Supply chain:** Dependabot, `pip-audit` and CodeQL in CI, actions pinned by commit, a software bill of materials and **GitHub build attestations** attached to releases.
7. **Tests:** fuzz/property tests for mask/unmask and chunking, the new injection corpus, placeholder-collision cases, cookie/origin/CSP tests.
8. **Docs:** `docs/THREAT_MODEL.md`, updated `SECURITY.md`.
- Done when: all tests pass; the packaged app smoke test passes with the cookie flow; a header check script shows CSP present.

### WP9b — Built-in auto-updater (like kinoz)
Copies the behavior from your kinoz README and PRIVACY.md.

- **Timing:** about 8 seconds after start, at most once a day.
- **The request:** a plain `GET` to `https://api.github.com/repos/p4inz-code/TextRepairo/releases/latest`, generic `User-Agent: TextRepairo/<version>`, no user id, no text, no system info. GitHub sees the IP like any request. No server of yours is involved.
- **Download:** real progress bar (same progress component as WP2, real byte counts). Verified against the published **SHA-256** (`SHA256SUMS.txt` on the release). Mismatch means the file is deleted and nothing installs. (SHA-256 only, your choice: it proves the file is intact, not who published it. I will say that plainly in `SECURITY.md`.)
- **Install:** Windows installer build only. Dialog "Restart now / Later". If Later, it installs on the next launch. On failure the old version stays. macOS, Linux and the portable zip only notify and open the release page.
- **Safe mode:** if the app ends abnormally twice, it starts in safe mode (like kinoz): updates and engine auto-start off, Doctor opens.
- **Release side:** the release workflow keeps publishing `SHA256SUMS.txt` (already does); the updater reads the right asset for the platform from the release.
- **Privacy text changes honestly:** README, About and `PRIVACY.md` will say the only network use is (1) the optional update check, and (2) downloads you start yourself (models from Hugging Face, the engine from GitHub). The current README claim "no network after setup" gets corrected.
- Files: new `updater.py`, `server.py` endpoints, `web/*`, `cli.py` (`textrepairo update --check`), `config.py` (mode, last-check time), `packaging/windows/installer.iss` (silent install support), tests with a fake release server.

The update address can be overridden only when running from source or with an explicit test flag, only to a loopback address, and never in the installed build.
- Done when: tests cover each mode, daily limit, bad checksum rejected, failed install keeps the old version; a full update (check, download with progress, verify, install, restart) works on the packaged Windows build against the local fake server.
